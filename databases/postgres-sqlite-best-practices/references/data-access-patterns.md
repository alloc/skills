# Data Access Patterns

Use this reference for application data-access code, prepared statements, ORMs, query builders, batching, pagination APIs, and N+1 issues.

## Parameterization

Never build SQL by interpolating untrusted values:

```ts
// Bad
db.query(`SELECT * FROM users WHERE email = '${email}'`);

// Good: placeholder style varies by driver
db.query("SELECT * FROM users WHERE email = $1", [email]);
```

When writing examples, follow the placeholder convention already used by the project.

## Query Ownership

- Keep SQL close to the data-access function that owns the use case.
- Name functions by domain action, not by table plumbing.
- Return shaped data that the caller needs; avoid leaking broad row objects when the API should be narrower.
- Keep engine-specific SQL behind a repository/adapter boundary.

## ORMs and Query Builders

- Inspect generated SQL for nontrivial queries.
- Verify migrations generated by ORMs before applying them.
- Do not assume ORM-level relations enforce database foreign keys.
- Use raw SQL for queries that are clearer, safer, or materially faster than a forced abstraction.
- Keep transaction APIs explicit; passing a transaction handle is often safer than relying on ambient state.

## N+1 Queries

Detect loops that query per row:

```ts
for (const user of users) {
  user.posts = await getPosts(user.id);
}
```

Prefer one set-based query, a join, batching, or a loader pattern:

```sql
SELECT *
FROM posts
WHERE user_id = ANY($1);
```

For SQLite examples, use the project driver's supported parameter expansion or generate placeholders safely.

## Batching

- Batch inserts and updates when many rows are written together.
- Keep batch sizes bounded.
- Use transactions around batches that should be atomic.
- Avoid huge `IN` lists that exceed driver or engine limits.
- Use temporary tables or staging tables for very large set operations.

## Pagination APIs

Expose stable cursors for large lists. Include a deterministic tie-breaker such as `(created_at, id)` to avoid duplicate or missing rows when many records share the same timestamp.

## Error Handling

- Map unique and foreign-key violations to domain errors at the boundary.
- Preserve enough detail for debugging without leaking SQL or secrets to end users.
- Treat transient transaction conflicts differently from permanent constraint failures.

## Smells

- SQL strings assembled from request fields.
- ORM migration accepted without reviewing generated DDL.
- Query in a loop over parent rows.
- Data-access layer hides whether work participates in a transaction.
- Portable library exposes Postgres-only SQL in its public API.
